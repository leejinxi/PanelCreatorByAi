## 二、方案路线 Review

### 2.1 路线演进是自洽且合理的

对比 4 份 Plan 文档与代码，方案经历了一次明确的收敛：

| 阶段 | 定位面/工程对象存在性 | 证据 |
|---|---|---|
| 旧路线（08-21 Provider/MCP Schema v1.0） | Agent 主链路内用 `list_reference_planes` 解析并**由 Provider 确认对象存在** | `Doc/Plan/CAD_Provider接口与MCP_Schema及Mock_MCP方案_v1.0.md` |
| 新路线（09-08 浏览器方案起，09-09 MCP PoC 定稿） | Agent **不查目录、不判存在**；只做已知标尺面确定性规范化，未知名称**原文直传 CAD**，由 CAD 返回 `REFERENCE_PLANE_NOT_FOUND`；契约仅保留 `create_panel` | `Doc/current_status.md`、`agent/graph.py`、`contracts/FULL_contract_with_data.json` |

**对路线的评价**：
- 这一演进方向正确：避免 Agent 维护工程对象快照/缓存，把“存在性”收敛到唯一权威方（CAD），减少 Agent 与 CAD 之间的状态漂移。
- 主链路 `parse → validate → cad` 边界干净：`agent/graph.py` 只有 3 个节点，条件路由只区分重试/CAD/结束，无 MCP SDK、Tool 名或传输细节泄漏，符合“Graph 不依赖具体 CAD 实现”的约定。
- 契约先行 + Contract Mock 是务实策略：`outputSchema` 用 `oneOf` 强制成功/失败负载互斥，与 `CadExecutionResult.model_validator` 双端对齐；未来换公司正式契约只动 JSON 和后端选择，上层流程不受影响。

### 2.2 遗留 Resolver 的处理（需要明确）

`tools/reference_plane_tools.py` + `schemas/reference_plane_schema.py` + `tests/test_reference_plane_tools.py` 属于被替换的旧路线，已不参与主 Graph（`graph.py` 未引用）。现状是“保留 + 有测试 + 不再被调用”，会造成三份文档历史歧义。建议显式标注为“历史模块，勿接入主链路；待删除或隔离到 `deprecated/`”，或在 TODO 中给出明确清理计划，避免后续 AI/维护者误接回。

### 2.3 浏览器演示方案（Step 1–3 已落地，Step 4 缺失）

- Step 1–3（标尺面规范化/名称直传、FastAPI Web API、单页工作台）均已实现并通过测试。
- Step 4（可控失败场景：直接 Mock 后端在特定输入下返回 `CAD_UNAVAILABLE` / `REFERENCE_PLANE_NOT_FOUND`）的代码“实现过但未保留”（文档自述），对应 `Doc/TODO.md` P1 首条，仍是明确待办。注意当前 MCP Mock 已能通过契约 `mockResponses` 模拟这两类失败，若演示只走 MCP 模式则缺口已覆盖一半；直接 Mock 的失败注入仍缺。

## 三、代码逻辑 Review

### 3.1 优点（值得保持的模式）

- **强类型边界双端校验**：`PanelRequest`/`PanelCandidate`/`CadExecutionResult`/`AgentActionPlan` 全部 `extra="forbid"`；成功/失败互斥在 Schema 与 MCP 契约两侧都强制，非法组合在数据层即被拒绝。
- **安全路由正确**：缺参→`clarification`、非法参数→`error`、`unsupported`→不触发 CAD；`validate_structure` 在未生成 `panel_request` 前绝不进入 `cad` 节点，测试通过 spy 断言 `build_cad_backend` 未被调用。
- **已知标尺面确定性规范化**：`ruler_plane_tools.py` 用纯正则（非 LLM）做 `第100肋位→FR100`，LLM 漏抽时再从原文兜底抽取，符合“模型只负责语言理解”。
- **LLM 输出容错**：非法 JSON 最多重试 1 次并携带错误信息回注 prompt；`LocalQwen` 对超时/连接/HTTP/无效响应做分类并带 `retryable`。
- **稳定错误码 + 不泄漏内部细节**：`CreatePanelTool` 把未知异常收敛为 `CAD_INTERNAL_ERROR`，测试断言 `sensitive` 不出现在 message 中；Web 层网络错误同理。
- **前端 DTO 隔离**：`AgentRunResponse` 不暴露 `llm_raw_output` 等内部状态；状态分类（success/clarification/unsupported/error）与步骤条渲染一致。
- **跨 PC 规则遵守良好**：路径全部经 `Path(__file__).resolve()` 推导，无个人盘符硬编码。

### 3.2 发现的问题

#### P1（建议尽快处理）

1. **状态/入口文档与代码不一致（误导风险最高）**
   - `AGENTS.md`（工程上下文入口）仍描述主链路含“3. `resolve_plane`：优先依据用户原文……匹配名称、别名或坐标”，并写“安全边界：定位面未找到、歧义、名称/坐标冲突时停止”。**实际 `graph.py` 没有 `resolve_plane` 节点**，这些分支已不参与主链路。
   - `README.md` 声称“按工程名称、别名或坐标表达式解析定位面 / 检测定位面未找到、歧义和名称/坐标冲突”，且未提及 MCP Mock 已存在，与当前能力不符。
   - `Doc/TODO.md` P0 多数条目（build_cad_backend 选择、`CAD_BACKEND=mcp`、`/api/health` 报告 mcp、全链路测试）**已实现但未勾选**；`Doc/current_status.md` 仍写“`McpCadBackend` 尚未接入 `agent/graph.py` 的运行时选择”与“94 项测试”，实际 `tools/cad_tools.py:create_panel()` 已按 `CAD_BACKEND` 环境变量选择后端、测试已是 115 项。
   - 建议：先提交本批代码改动，再一次性同步 AGENTS.md/README/current_status/TODO 四份状态文档，并在 AGENTS.md 增加版本日期标注，避免后续 AI 被旧路线误导。

2. **MCP 后端每次调用都冷启动子进程 + 全量握手**
   `tools/mcp_cad_backend.py:create_panel` 每次请求都经 `StdioMcpClient.call_tool` → `asyncio.run` → `stdio_client` + `initialize` + `list_tools` + `call_tool`，即**一次板架创建 = 一个新 MCP server 子进程**。
   对 PoC/测试无碍，但真实 CAD 场景下连接生命周期、鉴权、事务与调用频率都要求“一次会话服务多次调用”。建议在 CadBackend 抽象层预留“backend 实例缓存/复用”或“会话级 backend”，让真实接入时不重写 Graph。

#### P2（改进项）

3. **MCP 协议错误归类过粗**
   `McpCadBackend` 用宽 `except Exception → MCP_UNAVAILABLE` 兜底，把 `McpProtocolError`（tool 未广告、缺 `structuredContent`——本质是**契约/版本不匹配**）也归为“服务不可用”，掩盖了真正的问题类型。建议在 `StdioMcpClient` 层区分协议错误并映射为更精确的错误码（如 `MCP_PROTOCOL_ERROR`/`MCP_INVALID_RESPONSE`）。

4. **配置硬编码点待配置化（文档已自认但仍存在）**
   `llm/qwen_client.py` 中 `url=http://localhost:11434`、`model_name=qwen2.5:7b`、`timeout=120`、`temperature=0` 写死在默认字段；`agent/graph.py` 的 `MAX_MODEL_RETRIES`、标尺面范围 `RULER_PLANE_RANGES` 也硬编码。按 AGENTS.md“不得增加新的硬编码点”，建议用环境变量/配置文件收敛（Ollama 地址、模型、超时、标尺范围），这关系到换 PC/内网部署。

5. **Web 成功消息被模式文案无条件覆盖**
   `webapp/response_mapper.py:_map_cad_result` 后对 `success` 结果按 `mode` 覆盖 `cad_result.message`，后端真实 message 被丢弃。当前 mock/mcp 阶段合理（避免泄漏英文/内部消息），但将来接入真实后端并新增 mode 值后这段逻辑会成为错误来源——建议把“覆盖模拟文案”限定在 `mode in {"mock","mcp"}` 且未来真实 mode 走原 message 的意图用注释或常量显式固化。

6. **前端文案在 mcp 模式下仍有 “Mock CAD” 字样**
   `webapp/static/index.html`/`app.js` 的兜底文案（如 `result-meta` 初始 “Mock CAD 不会修改真实工程。”）在 `CAD_BACKEND=mcp` 时也会出现。虽不违反“不得声称真实 CAD 已连接”，但建议 `renderExecutionMode` 成功后联动更新兜底文案为当前模式，保持一致观感。

#### P3（提示 / 备忘）

7. **`thickness` 宽容解析**：LLM 若回显 `"14mm"` 字符串，`PanelCandidate.thickness` 宽松转换会失败并触发一次重试。Prompt 已约束“使用毫米数值”，属可接受残余风险；如实测模型频繁违规可加后处理或允许模式 `数字+mm`。
8. **契约 mock 按顺序匹配**：`mcp_mock/server.py` 用 `response_matches` 顺序取第一个命中，若未来 mock 场景在条件上互相包含（如同时命中 MISSING 与 UNAVAILABLE），结果取决于数组顺序——建议在契约文档显式声明“首条命中优先”并约束场景互斥。
9. **无服务端超时/幂等**：LLM 调用最长 120s，Web 请求无服务端超时与取消语义；前端已做 `isExecuting` 防重复提交，但页面刷新/重发仍可能重复创建（TODO P1 已意识到，此处再次确认需“停止等待≠服务端已取消”提示）。
10. **`/api/health` 语义是“配置模式”而非“探活”**：`status:"ok"` 只表示 backend 名可识别，不探测 Ollama/CAD 连通性。schema 注释已说明，建议前端文案不要把它渲染成“服务健康/已连接”，以免演示时被误读。
11. **`map_agent_state` 构造异常未被捕获**：`webapp/app.py:run_agent` 中 `map_agent_state` 在 `try/except` 之外，若内部状态组合触发 `AgentRunResponse` 校验异常会落到 FastAPI 500（非结构化 JSON）。当前各分支已兜底，概率低，可作为防御性改进。
