# 板架边界必填、表达式解析与匹配方案 v1.0

日期：2026-09-10
状态：最低边界数由4条改为1条；符号透传原则不变。Step 1–2 已接入主流程，Web 已同步列表；0.2-poc 已按用户确认启用为本地 MCP 演示契约（boundary_list_0.2.json）；历史草案保留，对象匹配仍待实施。以下现状表记录初始基线，最新状态见 ../current_status.md。
依据：当前 main 基线 7a957ec，以及用户新增的板架边界要求。
优先级：先完成边界业务闭环，再扩展 Agent 多工具选择展示。

## 1. 目标与业务约束

- 创建板架必须由用户提供边界；缺失时提示补充，不调用创建工具。
- 至少提供 1 条有效边界，支持超过 4 条，不限制为固定的上、下、左、右。
- 每条输入为 `<` 或 `>` 加边界对象/标尺面名称，例如 `<SL10`、`>LV2`。
- 推荐按规范化后的方向符号和目标名称去重计数；重复输入不增加有效边界数。
- 标尺面处理与当前板架定位面规则一致：已知名称确定性规范化，其他工程名称保留原文，由 Provider 判断存在性和可用性。
- LLM 不得补造缺少的边界，不得擅自添加或翻转方向符号，不得把边界目标当作定位面。
- 已确认：`<`/`>` 仅作为不透明的接口符号解析、保留并传给 CAD；Agent 和本地 Mock 不解释符号与模型的关系，不进行正负侧、法向、闭合性或几何冲突判断。
- 当前 Provider 使用本地 Mock 数据，不代表公司 CAD 的真实对象或几何验证。

推荐完整输入：

```text
在 FR100 创建板架，厚度 14mm，材料 AH36，边界为 >SL-10 <SL10 >LV2 <LV8
```

这里的四条边界只作为表达式示例，不承诺这些标尺面的实际坐标或闭合结果。

## 3. 输入语法与确定性解析

### 3.1 推荐支持范围

| 输入 | 处理 |
|---|---|
| `<SL10`、`>LV2` | 直接解析为方向和目标 |
| `< sl 10` | 已知标尺面规范化为 `<SL10` |
| `＞LV2`、`＜SL10` | 全角比较符规范化为半角，方向不变 |
| `>第100肋位` | 在已知范围内规范化为 `>FR100` |
| `>舱壁A` | 目标原文保持为舱壁A，由 Provider 匹配 |
| `<"Deck A"` | 含空格的工程名称使用引号，保留名称内部内容 |
| `SL10` | 缺少方向，提示用户补充，不推断 |
| `>`、`<   ` | 缺少目标，不计入有效数量 |
| `>=SL10`、`<=LV2`、`>>SL10` | 当前不支持，提示修正；不能截取为合法子串 |

推荐分隔方式：空格、逗号、中文逗号、分号或换行。含空格、分隔符或比较符的目标使用成对引号包裹；引号不完整时报错。首版不支持表达式嵌套、逻辑或、范围缩写和数学求值。

解析器须识别完整边界片段及其原文位置，不能只匹配其中合法部分后忽略剩余内容。未识别的边界片段仍须展示问题，即使其余有效边界已经达到 1 条也应暂停。

### 3.2 与定位面相同的名称规范化

复用 tools/ruler_plane_tools.py 的规范化行为：

- 当前已知范围：FR-10～FR200、SL-40～SL40、LV-5～LV50。
- 统一已知前缀大小写、前缀与数字空格以及可识别的中文肋位写法。
- 只对目标名称规范化，`<`/`>` 不参与名称处理，不得改成另一方向。
- 范围外的名称不直接等同于“不存在”；按当前定位面策略保留原文，交给 Provider。
- 未知工程名称不做模糊改名或擅自改变大小写；项目别名映射由 Provider 数据决定。
- 名称中的数字是标识的一部分，不能未经坐标数据就当作物理坐标或间距。

### 3.3 隔离定位面和边界

当前 extract_known_ruler_plane_name 会扫描整段输入；增加多条边界后会产生多个标尺面候选。

改造要求：先识别带比较符的边界片段，定位面兜底提取仅扫描其余明确的定位面语境。用户没有提供定位面时，即使边界含 FR/SL/LV，也必须提示补充定位面。LLM 输出与原文角色冲突时不得直接放行。

测试关键例：`创建14mm厚AH36板架，边界 >SL-10 <SL10 >LV2 <LV8` 必须提示缺少定位面。

## 4. 数据结构与契约设计

### 4.1 候选数据与执行数据分离

建议在 schemas/ 定义：

- BoundaryCandidate：原始片段、可空方向和可空目标，用于保留不完整输入；允许候选列表为空。
- BoundaryConstraint：operator 仅允许 `<` 或 `>`，target 为非空规范化名称，拒绝未知字段。
- BoundaryValidationIssue：问题码、关联边界序号、可公开的问题描述。
- PanelCandidate：允许缺失边界，以便进入澄清而不是触发模型格式重试。
- PanelRequest：必填 boundaries 列表，至少 1 条；按符号与规范化目标组成的完整项去重，不校验几何冲突；拒绝旧四向对象。

原文、来源轮次和匹配状态作为内部状态或 Web 展示数据保存，不混入 CAD 执行字段。用户输入错误与模型 JSON 错误分开处理，不能通过反复调用 LLM 自动凑齐边界。

拟议 MCP 输入：

```json
{
  "referenceName": "FR100",
  "thicknessMm": 14,
  "material": "AH36",
  "boundaries": [
    {"operator": ">", "target": "SL-10"},
    {"operator": "<", "target": "SL10"},
    {"operator": ">", "target": "LV2"},
    {"operator": "<", "target": "LV8"}
  ]
}
```

新版 JSON Schema 对 boundaries 设置 type=array、minItems=1、uniqueItems=true；每项必填 operator/target，operator 使用枚举，target 拒绝空白，additionalProperties=false。规范化后的去重、别名指向同一对象及对象存在性由业务层/Provider 校验，不能仅依靠 uniqueItems。

### 4.2 契约版本迁移

这是破坏性变更：四向对象不能自动映射成四条带方向边界，更不能猜测上下左右对应的坐标方向。

- 保留 Git 中已确认的 0.1-poc 基线，先新增 0.2-poc 草案文件供确认。
- 草案不得标记 confirmed；当前 load_contract 拒绝未确认契约，方案确认后再完成新版契约审核、状态更新和运行默认切换。
- 新旧版本不静默混用；旧版的空边界和无符号四向输入在新版本明确拒绝。
- 同步升级 Agent、PanelRequest、McpCadBackend、直接 Mock、Web Schema、示例、测试和操作文档。
- agent/execution_trace.py 当前写死 0.1-poc，升级时改为记录实际加载契约的版本。
- create_panel 输出继续遵守成功/失败互斥：失败不得包含对象 ID。

## 5. 校验与匹配责任

### 5.1 Agent：输入完整性和确定性检查

推荐顺序：

1. 根据当前需求和补充记录整理边界原文。
2. 解析完整表达式，保留符号和来源。
3. 规范化已知标尺面名称。
4. 检查缺失、非法符号、空目标及未识别片段。
5. 对相同 operator + 规范化 target 去重，展示有效条数。
6. 至少 1 条格式有效且不重复的完整项，且无未解决的输入问题，才构造 PanelRequest；不检查比较符的几何含义。
7. 按现有流程调用 Provider。

同一目标出现 `<SL10` 和 `>SL10`：视为两条不同表达式，保留并传给 CAD，不自动判冲突、不删除、不合并；是否满足正式 CAD 的业务要求由 CAD 判断。

不能把“至少 1 条”改成“必须两个大于号加两个小于号”，也不要求用户说明符号的几何方向。

### 5.2 Provider：工程对象匹配和创建前检查

推荐在 create_panel 内先完成全部目标匹配和可用性检查，任一失败均不得创建模型或返回成功对象 ID；本期不要求新增独立查询 MCP API。

匹配规则：

- 精确名称或 Provider 明确维护的别名能唯一匹配，才接受。
- 未匹配：返回 BOUNDARY_TARGET_NOT_FOUND。
- 多个匹配：返回 BOUNDARY_TARGET_AMBIGUOUS，不自动选第一个。
- 对象类型被 Provider 数据明确标记为不能作为边界：返回 BOUNDARY_TARGET_UNSUPPORTED；本地不检查取侧条件。
- 多个名称指向同一个对象且符号相同：按对象 ID 与符号复核重复；符号不同不据此判定冲突。
- 名称匹配和输入检查完成后，将符号与目标对应传入 CAD 接口；真实几何闭合、相交关系、裁剪区域有效性由正式 CAD 负责，本期不实现。

本地 PoC 建议在新版契约添加明确标注的 mockData：已知标尺面、少量边界对象、别名、模拟 ID、可用对象类型和失败场景。直接 Mock 与 MCP Mock 共用同一套校验规则，避免不同启动模式行为不一致。

目前 mockResponses.match 只做顶层等值比较，不能表达逐条对象匹配；需增加小型确定性 Mock 校验器读取 mockData。旧默认成功兜底必须放在检查通过之后。本期 Mock 不模拟符号的几何含义，也不宣称验证了真实闭合边界。

### 5.3 状态必须准确

- 缺失、没有有效边界、非法格式：Agent 澄清，MCP 未调用。
- 对象不存在/歧义：可能已经调用 MCP，但 Provider 拒绝创建，不能显示“MCP 未调用”。
- 已知无创建副作用的边界业务拒绝可进入补充流程，保留问题码和失败调用记录。
- 超时、通信失败或创建结果不确定：维持受控错误，不自动重新调用创建；不能当成补充边界后可以无条件重试。

## 6. 多轮补充与修正

例一：缺少全部边界。

```text
用户：在 FR100 创建14mm厚AH36板架。
系统：还需要至少1条边界，每条使用“<或> + 对象/标尺面”。请补充边界。
用户：边界 >SL-10 <SL10 >LV2 <LV8。
系统：已收到4条有效边界，继续校验和提交。
```

例二：已有边界时补充其他参数（数量已合格）。

```text
用户：在 FR100 创建14mm厚板架，边界 <SL10。
系统：已收到1条有效边界，数量合格；还需补充材料。
用户：材料 AH36。
系统：保留原有边界、定位面和厚度，继续校验和提交。
```

处理规则：

- 明确“补充/再加”表示追加，不覆盖已接受项。
- “将 <SL10 改为 <SL12”只替换明确对应项；匹配不唯一则澄清。
- “边界全部改为……”整体替换，旧边界不能再次参与计数。
- 无法确定用户是在追加还是替换时，请用户确认；不能仅因为同一目标出现不同符号就发起冲突澄清。
- 不确定的自然语言修改不能单凭模型输出覆盖已确认表达式。
- CLI 和 Web 使用同一个边界合并规则；当前拼接历史文本的方式要增加结构化边界状态或按轮次可靠解析，不能对整段历史直接做集合并集。
- 超出 CLI 补充轮数时安全结束，不因为缺少边界而放宽限制。

## 9. 验收矩阵

| 场景 | 预期 |
|---|---|
| 未提供、空列表、null | 提示至少1条；不调用创建 |
| 1～3条有效项 | 数量合格，继续校验和 Provider 匹配 |
| 恰好1条且 Provider 接受 | Mock 成功，参数和符号不变 |
| 5条或更多 | 不截断；逐条校验，全部传输 |
| 缺比较符、空目标、>=、<=、重复比较符、未闭合引号 | 指出错误，不静默丢弃 |
| 重复4次同一项 | 去重后计1条，数量合格，继续其余校验 |
| 4条合法项外另有非法片段 | 仍要求修正 |
| 已知大小写/空格/中文肋位 | 与定位面规则相同的规范化 |
| 范围外标尺面、普通工程对象 | 保留原文，Provider 决定是否接受 |
| 模型虚构边界、反转比较符 | 原文核对阻止执行 |
| 边界包含多个标尺面、定位面缺失 | 仍提示定位面缺失 |
| 同一目标使用不同符号 | 两项分别保留并透传，不判几何冲突 |
| 同一符号且别名指向同一对象 | 按对象 ID 与符号识别重复，不增加有效数量 |
| 边界未知、歧义、类型不可用 | Provider 拒绝，不返回对象 ID |
| 无→1条 | 补充可完成，其他字段保留 |
| 显式替换一条、整体替换 | 旧项不复活，不隐式累加 |
| 直接调用新版 MCP，传旧四向对象/空数组 | 服务端拒绝，不能绕过 Graph |
| MCP 超时、异常、非法返回 | 受控错误，无自动创建重试 |
| Web 部分候选与失败响应 | 页面正常渲染，创建阶段是否调用展示准确 |

默认测试隔离真实 Ollama/CAD。更新所有受影响的成功 fixture 和真实 Ollama E2E 请求，使成功案例包含有效边界；真实 Ollama E2E 保持显式开启。

## 10. 已确认原则与推荐实施细节

符号透传原则已由用户确认，其余为本地 PoC 的推荐实施细节，不是公司 CAD 几何规则：

1. 已确认：暂时不理解大于/小于号与模型的关系，只需保留并传递给 CAD 接口。输入解析只验证符号为 `<` 或 `>`，不要求用户补充正负侧或法向定义。
2. “最少1条”推荐按规范化后的完整表达式计数：相同符号与相同目标不重复计数；同一目标不同符号保留为不同项。Provider 仅对同一符号指向同一对象的别名项复核重复。
3. 第一阶段推荐由 Provider 在 create_panel 内进行匹配并先验证后创建；独立 validate_panel_boundaries 或查询 API 留到需要提前展示候选时再扩展。

本期完成标准：用户不提供足够且合规的边界无法执行；足够边界经过真实 MCP 传输和明确的 Mock 匹配后能完成本地演示，且不把 Mock 判定描述为真实 CAD 几何验证。
